# G7 visual review 3, P8 payments, finance and workspace screens (2026-11-19)

Independent reviewer (did not build or fix the UI). No application code, CSS, lang, tests or config was changed and nothing was committed. Third review, after fix pass C (commit `5734b9d`). Baseline: `docs/reviews/G7_P8_REREVIEW_2026-11-19.md` (R1-R16, D-items). Same screen list, same six-dimension rubric (Ref, Vis, RTL, Resp, Sta, Con; 1-5; pass = mean >= 4.5 and every dimension >= 4). ## Method and environment
- Scratch SQLite DB in the scratchpad (`rv3.sqlite`, never `database/database.sqlite`), `migrate --force`, `demo:seed`, `APP_ENV=local`, `php artisan serve --port=8099`, repo-default `CACHE_STORE=file` (confirmed with `config:show cache.default`), `npm run build` run once. Server stopped at the end.
- Seeded through the app Actions (tinker), same scripts as the re-review: 3 refunds (executed / approved / pending), 3 ledger adjustments, instructor payout profile, 2 October statements, 1 draft settlement batch. Data-only tweak in the scratch DB: adjustment ledger rows back-dated to 2026-10-15 so a month could be frozen. Demo seed already has the active subscription (Nour). 2FA TOTP secret set on admin/finance/instructor in the scratch DB only.
- Tooling deviation (same as the earlier reviews): Playwright Chromium via node scripts (repo `node_modules`), not the built-in browser pane, because the pane cannot write PNGs into the repo.
- Viewports 1440x900 and 390x844, Arabic and English, light; dark for catalog, checkout order and admin dashboard. Guests use `/ar` and `/en`; logged-in users follow `users.locale`.
- How I read: a contact sheet (AR 1440, EN 1440, AR 390, EN 390) for every screen, plus zoomed crops where something looked wrong (dashboard KPI strip, checkout AR discount). Not pixel-measured; no contrast ratios; scores are visual judgements. Finance reports was captured and verified by DOM text but its sheet was not individually viewed (identical component to admin reports); not scored separately.
- Capture caveats: full-page captures render the fixed learner tab bar and the mobile sticky price bar in the middle of the page (artefact, not a defect). My first AR-390 checkout capture landed on `/my` because a forced radio click hit the fixed tab bar link; I re-captured it by script (`checkout-order-ar-390*.png` use a fresh order 10, no coupon). `checkout-coupon-applied-*` and `fake-gateway-*` are of order 9, which by then also had a gateway attempt (a "confirming payment" banner shows on it at 390).
- Reports check: the system clock was 23:54 UTC on 18/11 (01:54 in Egypt on 19/11) when the demo orders were created, so all 5 paid orders were paid "today in Egypt" but "yesterday in UTC". With the default range, admin and finance reports show inputs 2026-10-21 to 2026-11-19, caption "Showing 21/10/2026 to 19/11/2026", and 5 paid orders, EGP 2,960.00 sales, 350.00 refunded, 2,610.00 net. Inputs, caption and query agree.

## Recommendation on the threshold question
Do not lower 4.5 for the public and checkout screens: they sit at 4.1-4.2 and the gap is concrete, fixable polish (cover art, density, mobile order of checkout summary). For the staff and learner screens with no reference in the pack, a 4.5 bar measured against a reference is not satisfiable in principle; score Ref against the design-system rules and keep the remaining five dimensions at the same strictness. Even then, three S2 regressions (N1, N2, W1) introduced by the last CSS pass must be fixed first: they hold the dashboards and Filament screens below 4.0 on Resp/Vis. Realistic target after those fixes: public/checkout 4.4-4.5, staff screens 4.2-4.4; a per-screen-class bar (4.5 public/checkout with reference, 4.3 staff without reference, every dimension >= 4) is a defensible PO decision, but it is the PO's call and none of the scores here were adjusted for it.
