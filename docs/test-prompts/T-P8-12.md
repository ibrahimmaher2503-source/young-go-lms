You write the tests for a finished task. Do **not** change production code (`app/**`, `database/**`, `routes/**`, `config/**`, `resources/**`, `lang/**`). If a test exposes a bug, write it correctly, mark it `->skip('BUG: ...')` and list it in `docs/reviews/BUGS_FOUND.md`.

## What was built
- Routes (all in `routes/pages.php`, auth group): `GET /checkout/{course|bundle}/{id}` (`checkout.product`), `POST /checkout/start` (`checkout.start`, throttle 20/min), `GET /checkout/orders/{order}` (`checkout.order`), `POST|DELETE /checkout/orders/{order}/coupon` (`checkout.coupon.apply|remove`, throttle 10/min and 20/min), `POST /checkout/orders/{order}/pay` (`checkout.pay`, throttle 10/min), `GET /checkout/return?order=<reference>` (`checkout.return`, the path from `config('payments.return_path')`).
- `CheckoutController` (thin): payer is always `$request->user()`, never the acting child. `product` shows the learner step (self plus verified children, default = acting learner, learners who already hold the course are disabled) and a price preview; 404 when the product is not sellable. `start` validates type/product/learner/key, learner must be in `CheckoutLearners`, then `StartCheckoutOrder`. `order` shows the stored server state: paid (courses link, receipt link), failed/cancelled/refunded/disputed notice, pending with proof pending, pending with open gateway session, or the pay form (coupon card, method radios, terms checkbox). `applyCoupon`/`removeCoupon` call `ApplyCoupon`/`RemoveCoupon`. `pay` validates `method` (enabled gateway methods plus `manual`) and `terms` (`accepted`); `manual` redirects to `manual-payments.create`; a gateway method calls `StartCheckout` and redirects away to its checkout URL. `return` looks the order up by reference scoped to the payer (404 otherwise) and redirects to `checkout.order`; it writes nothing and ignores every other query parameter.
- `Queries\CheckoutOffers` (`coursePrice`, `bundle`): published, individually sold (`INDIVIDUAL_ACCESS_MODES`), priced in an active market; bundles through `PublicBundles` with a price. `Queries\CheckoutLearners`: payer first, then verified active children if the payer has role parent.
- `Actions\StartCheckoutOrder`: returns the payer's existing pending single-line order for the same product, learner and market, else `CreateOrder` with the given idempotency key.
- `Actions\ExpireAbandonedOrders` + command `orders:expire-abandoned` (scheduled hourly in `routes/console.php`): cancels pending orders older than `config('payments.order_ttl_hours')` (24) through `TransitionOrder` (releases the reserved coupon use). Skips orders with an open payment attempt (`active_order_id` set) or a pending manual proof. Returns the count.
- CTA: `catalog/_cta.blade.php` shows a "Buy now" link (`data-cta="buy"`) to `checkout.product` for a signed-in, not-enrolled user when `PublicCourseController` passes `purchasable` (course in `CheckoutOffers::coursePrice`); signed-out keeps the sign-in link; entitled keeps continue; everything else keeps the disabled "soon" button.
- Config: `payments.order_ttl_hours`, `manual_payments.payee` (env `MANUAL_PAYMENT_PAYEE`, empty by default; the owner has not supplied the Instapay/bank details, UNKNOWN). Lang `lang/ar|en/checkout.php`. No new audit event (existing `order.created`, `coupon.*`, `payment.*` are reused).
- Views: `resources/views/checkout/{product,order,_summary}.blade.php` on `x-layouts.learner`.

## Acceptance
- A1 Full journey with the Fake gateway grants access only after the webhook: sign in, open `/courses/{slug}`, click buy, pick learner, continue, agree to terms, pick `card`, pay; the response redirects to the Fake checkout URL (`https://fake-gateway.test/...`); before the webhook `EntitlementService` denies and the order page (`checkout.order`, also via `checkout.return?order=REF`) shows the awaiting state; after a signed fake callback through `/webhooks/paymob` (see T-P8-03) the order is paid, access is granted and the order page shows `checkout.status_paid`. The return page alone never marks anything paid, even with `?success=true` style parameters. Browser test optional; HTTP-level test is enough.
- A2 Abandoned orders are released: a pending order with a reserved coupon older than the TTL is cancelled by `ExpireAbandonedOrders`, the coupon `redemptions_count` goes back, the redemption is released. Not touched: a younger order, an order with an open `PaymentAttempt`, an order with a pending proof, a paid order. A payment that is then verified for a still-pending order is unaffected.
- A3 Screenshots AR/EN x mobile/desktop: not in this task (G7 open, see gaps).

## Also cover
- Auth and scope: signed out is redirected to login on every checkout route; another account (including a parent for a non-linked child, or a child for the parent's order) gets 404 on `checkout.order`, coupon, pay and return; an unknown or foreign `order` reference on return is 404; a non-sellable course (draft, free-only, subscription-only, no EG price, inactive bundle, bundle with a draft course) is 404 on `checkout.product` and `checkout.start`.
- Learner step: a parent sees self and verified children (not pending links, not another parent's child); in child context the acting child is preselected; start with a learner outside the list is a `learner_id` validation error; a course the learner already holds is refused with `commerce.already_enrolled` (`order` bag) and the option is disabled on the product page; bundle with a partly owned set still starts.
- No pile-up: starting twice for the same product and learner returns the same pending order (one `orders` row, one `order.created` audit); a failed or cancelled order for the same product is not reused; double submit with the same key is safe.
- Coupon: apply a valid code updates subtotal, discount and total on the page; wrong code shows the `coupon` bag message (`commerce.coupon_invalid`); applying a second code shows `coupon_already_applied`; remove restores the total and gives the use back; the apply route is throttled (11th request in a minute is 429); a coupon change after a gateway session was opened makes the next pay create a fresh session (StartCheckout behaviour).
- Pay validation: missing `terms` gives `checkout.terms_required`; missing or unknown method gives `checkout.method_required`; with the Null gateway (`PAYMENTS_GATEWAY=null`) only manual is offered, the unavailable notice shows, and posting `card` is rejected; manual redirects to `manual-payments.create` and the proof form still works end to end (T-P8-04), after which the order page shows the proof-pending state and hides the pay form; a rejected proof shows the rejected notice and the pay form again.
- Money: the page shows server amounts only (tamper with posted `price`/`total` fields: ignored); amounts render in AR and EN formats; order totals frozen once paid.
- Status pages: failed and cancelled orders show their notice and no pay form; paid shows the courses link and a working receipt link; refunded/partially refunded/disputed show their notice.
- Public CTA: signed-in non-enrolled learner on a paid course with an EG price sees `data-cta="buy"` linking to checkout; a free or priced-less course keeps `data-cta="soon"`; signed-out keeps `data-cta="sign-in"`; enrolled keeps `data-cta="continue"`.
- Terms link: when the CMS page with seed key `terms` is published the checkbox shows its locale URL; otherwise the link is omitted and the page still works.
- Lang parity: `lang/ar|en/checkout.php` have the same keys; `app:check-translations` and `app:check-rtl` pass; pages render in AR (rtl) and EN with no missing keys. Arch: controllers/Actions stay final, `App\Domain` has no HTTP imports.
- Scheduler: `orders:expire-abandoned` appears in `schedule:list`; the command prints the count.

## Known gaps (do not test as working)

- No public bundle page or bundle index: checkout accepts `bundle` ids and `CheckoutOffers::bundle` exists, but no CTA links to it yet.
- Plan (subscription) lines are T-P8-08 and are not part of this UI.
- Terms acceptance is validated per request, not stored or audited.
- The return page does not auto-refresh; the pending state has a manual "Refresh status" link.
- Manual transfer payee details are UNKNOWN (`MANUAL_PAYMENT_PAYEE` empty shows generic text). Real Paymob is blocked by B-07. The learner name/email read-only fields from the reference are not shown (the payer is the signed-in account).
