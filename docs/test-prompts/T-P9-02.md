## What was built
- Tables (`2026_11_18_143000_create_engagement_tables`): `wishlists` (user_id, course_id, created_at; unique pair, cascade) and `course_reviews` (course_id, learner_id, rating 1-5, body, `author_name` snapshot, status `pending|published|rejected|hidden`, moderated_by, moderated_at, moderation_reason; unique course_id + learner_id). The migration also grants the new permission `review.moderate` to an already-seeded `admin` role; `config/permissions.php` grants it to `admin` (super_admin has everything).
- Config `config/engagement.php`: `reviews.body_min` 10, `body_max` 1000, `children_may_review` true, `public_per_page` 10, `rating_cache_seconds` 86400.
- Domain `App\Domain\Engagement`: models `Wishlist`, `CourseReview`, enum `ReviewStatus`; `ReviewerName` (display snapshot: first name + last initial, e.g. "Mona K."; display_name is used for adults; a child account (guardian link as child, or under `ai.adult_age`) always uses the account name, never display_name; single-word name gives just the word; empty gives `engagement.anonymous`); `ReviewSummary::for($course)` (cached `{average, count}` over published only; `forget()`); `ReviewModeration` (shared transition: needs active actor with `review.moderate`, row lock, audit, cache drop, one notice).
- Actions (all final): `ToggleWishlist(User, Course): bool` (true = saved; only a Published course can be added; removal always works; inactive user = AuthorizationException; unpublished add = ValidationException `course`), `SubmitCourseReview(User, Course, int $rating, string $body)` (needs an active user, not parent context, a current entitlement via `EntitlementService::canAccessCourse`, rating 1-5, body 10-1000 after trim; first call creates a `pending` row, later calls edit it and put it back to `pending` clearing moderation fields, so a published review that is edited leaves the public page and the rating cache is dropped; a `hidden` review cannot be edited (ValidationException `review`); a rejected one can; audit `review.submitted`), `ApproveCourseReview` (pending or hidden to published; reason optional; no-op on published), `RejectCourseReview` (pending only; reason 10-1000 required), `HideCourseReview` (published only; reason 10-1000 required). Moderation without `review.moderate` or by an inactive user = AuthorizationException; wrong from-state = ValidationException `review`; each change audits `review.published|rejected|hidden` (before/after status, reason, course_id), drops the rating cache, and sends one `ReviewDecisionNotice` to the learner (dedupe per review, status and moderated_at; a rejection body contains the reason, a hidden one does not).

## Acceptance
- A1 Non-entitled cannot review: a signed-in learner with no entitlement (also an expired or revoked one, and a user with only a wishlist row) gets 403 from `POST reviews.store` and `SubmitCourseReview` throws; no row is created. A guest is redirected to login. An entitled learner creates exactly one `pending` row; sending again edits the same row (still one row, `pending`).
- A2 Pending reviews are not public: with a pending, rejected and hidden review the course page shows no `[data-review]`, no summary, the section stays `hidden`, the JSON-LD has no `aggregateRating`, and `ReviewSummary` says count 0. After approval the review, the average and count appear and the JSON-LD contains `aggregateRating` with the right numbers. Hiding or editing it removes it again (cache is invalidated).
- G7 (UI in scope): screenshots AR/EN x 390x844 and 1440x900, light and dark, of the catalog with hearts, the course page reviews area (empty-for-guest hidden, with reviews, entitled form states pending/rejected), the saved courses page (empty and filled) and the admin `course-reviews` queue, in `tests/Browser/screenshots/T-P9-02/`. - Course page regression: existing public course page behaviour is unchanged (unpublished = 404, CTA states, JSON-LD without reviews has no `aggregateRating`, empty hidden `[data-reviews-slot]` when nothing to show); the catalog still renders for guests.
