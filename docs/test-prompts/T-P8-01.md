## Also cover
- Idempotency: same payer + key + same request returns the same order (one row, one `order.created` audit); same key with different lines or market gives `idempotency_conflict`; key shorter than 8 or with bad characters refused; two payers can reuse a key; line order does not change the fingerprint.
- Refusals: empty or more than 20 lines, duplicate course+learner, bundle/plan type (`product_unavailable`), draft/private/archived or free course, price 0 or missing (`price_unavailable`), learner already holding a current entitlement (`already_enrolled`; use `GrantEntitlement`), nonexistent course. A failed line rolls back the whole order (no partial rows).
- Totals: multi-line sum, `discount_minor` 0, `total = subtotal`, `allocated_minor = unit price`, integer columns, currency = market currency, reference format `YG-ORD-XXXXXXXXXX`, `request_hash` hidden from `toArray()`. Audit failure (bind a failing `AuditLogger`) rolls the order back.
- `TransitionOrder`: pending to paid sets `paid_at` once; allowed and forbidden moves for every status (use `OrderStatus::next()`); same-status call is a no-op with no extra audit; terminal states (failed, cancelled, refunded) refuse everything; audit `order.status_changed` before/after; audit failure rolls back.
- Immutability: after `paid`, `refunded`, `partially_refunded`, `disputed`, direct `$order->update(['total_minor' => ...])`, `subtotal_minor`, `discount_minor`, `currency`, `market`, `payer_id` throw `LogicException`; a status-only update still works; pending totals may be updated. `OrderItem` snapshot columns (`unit_price_minor`, `currency`, `learner_id`, `product_id`, titles) cannot be updated; `allocated_minor` and `discount_minor` can.
- `AdjustOrderTotal`: needs an active actor with `payment.approve_manual` (finance/admin yes, learner/instructor no, inactive no); reason 2 and 501 chars refused, 3 and 500 ok; discount below 0 or above subtotal refused; failed/cancelled orders refused; on a paid order it works, writes `discount_minor` and `total_minor = subtotal - discount`, leaves subtotal and items untouched, audits `order.adjusted` with before/after and the reason in context; the guard is closed again afterwards (a direct update still throws); audit failure rolls back.
- Race: pre-create an order with the same payer and key then call `CreateOrder` with the same request: returns it without a second row.
- Lang parity: every `commerce.*` key exists in AR and EN (`php artisan app:check-translations`), audit labels exist for the three events.
