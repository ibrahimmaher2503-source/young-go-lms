The discount is split across eligible lines by price (floor, leftover to earliest lines); `order_items.discount_minor` and `allocated_minor = unit - share` are written, `orders.discount_minor` and `total_minor = subtotal - discount`.
- Setup: create orders with `CreateOrder` (see `docs/test-prompts/T-P8-01.md`), staff with `Permission`-seeded finance/admin role.

## Acceptance
- A1 Rejected coupons (assert key and that nothing changed: order totals, `redemptions_count`, no redemption row): unknown code, lower-case or padded code still works, bad format, inactive, `starts_at` in the future (`coupon_not_started`), `ends_at` past or equal now (`coupon_expired`), over total cap (`coupon_exhausted`), over per-payer cap (`coupon_user_limit`), course-restricted coupon on an order without an eligible course (`coupon_ineligible`), fixed coupon in another currency (`coupon_ineligible`), order not pending (paid/failed/cancelled), order of another payer or inactive payer (`coupon_order_invalid`), second coupon on one order (`coupon_already_applied`).
- A2 Concurrent redemptions respect the cap: coupon `max_redemptions = 1` (and 2), several orders from different payers apply the same coupon; exactly the cap succeeds, the rest get `coupon_exhausted`, `redemptions_count` equals the successes. SQLite cannot run true parallel transactions, so also test the guarded counter directly: set `redemptions_count = max_redemptions` behind the Action's back after validation passes is not possible, so instead assert sequential exhaustion, and a stale `redemptions_count` never goes over the cap or below zero after apply/remove/release cycles. If your DB driver supports it, add a forked/parallel test and mark it `->skip` otherwise with the reason.

## Also cover
- Pricing: percent rounds down on odd amounts; 100% gives total 0; fixed larger than eligible subtotal is capped to it; multi-line order with a restriction discounts only eligible lines (`discount_minor` on ineligible items stays 0); item shares add up exactly to the order discount and never exceed a line price; `subtotal_minor` and snapshots are untouched; integer columns.
- Per-payer cap counts reserved and redeemed uses but not released ones; `max_per_user = null` means unlimited; the cap is per payer (another payer may still use it).
- `RemoveCoupon`: only the payer on a pending order with a reserved coupon; frees the use (`redemptions_count` back), deletes the redemption, restores totals and item allocation; then another coupon can be applied; refuses when none applied (`coupon_not_applied`).
- `TransitionOrder`: pending to paid marks the redemption `redeemed` with `redeemed_at` and writes `coupon.redeemed`; a retried paid transition is a no-op (one audit); pending to failed or cancelled marks it `released`, decrements the counter and frees the cap for another order; paid order totals stay frozen (Order guard) and the discount stays on the order; refund transitions do not release a redeemed use; an order without coupon transitions as before. Audit failure rolls the transition back.
- `SaveCoupon`: needs an active actor with `payment.approve_manual` (finance/admin yes; learner, instructor, inactive no, `AuthorizationException`); code normalised to upper case and must match `^[A-Z0-9_-]{3,32}$`, unique (also across edits); name 2..120; percent 1..100; fixed needs amount > 0 and a currency from `config('markets')`; `ends_at` after `starts_at`; caps >= 1 or null; unknown course ids refused; courses synced; audit `coupon.created` / `coupon.updated` with before/after; audit failure rolls back. After the first redemption row, code, type, percent, amount and currency cannot change (`coupon_frozen`) but dates, caps, courses and `is_active` can; `max_redemptions` cannot go below `redemptions_count`.
- `CouponUsage::for()`: counts redeemed, reserved, released and discount totals per currency (confirmed uses only), for all coupons and for one.
- Filament (Livewire test, admin and finance panels): list page renders for finance/admin and `payment.view` holders (no create/edit actions for view-only), not for learners/instructors; create modal creates a coupon via `SaveCoupon` and shows a danger notification with the lang message on a duplicate code; edit modal is pre-filled; fixed amount entered in major units is stored in minor units (12.50 EGP = 1250); status badge per state (active, scheduled, inactive, expired, used up); summary strip shows used/reserved/discount numbers.
- Lang parity: every new `commerce.coupon_*` key and `coupon.*` audit label exists in AR and EN (`php artisan app:check-translations`); `app:check-rtl` passes.
- Arch: `App\Domain` has no HTTP/Livewire/Filament imports; coupon Actions are final (existing `tests/Arch`).
- Known gaps: no checkout UI or HTTP endpoint (T-P8-12 must call `ApplyCoupon`/`RemoveCoupon` and rate-limit code attempts), abandoned pending orders keep their reserved use until the order is failed/cancelled (timeout job belongs to T-P8-12), no affiliate codes (out of scope), no G7 screenshots for the admin modal yet.
