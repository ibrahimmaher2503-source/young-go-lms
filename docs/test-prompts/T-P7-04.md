- Endpoint `POST api/v1/lessons/{lesson}/assistant/feedback` (`assistant.feedback`), body `{message_id, type: understood|not_understood}`. Replies: `200 {state: recorded}` (understood), `201 {state: request_created, request_id, thread_url, status}`, `200 {state: request_exists, ...}` on a repeated tap, `404 not_found` (not the learner's answer, other lesson, user message), `409 open_limit` (4th open request on the lesson) or `409 not_escalatable` (answers made by an input guard), `403` without `ai.ask`, `422` invalid type, `429` throttled.
- Learner thread: `GET /my/help/{helpRequest}` (`help.show`, 404 unless it is the acting learner's) and `POST /my/help/{helpRequest}/replies` (`help.reply`). Component `<x-learning.help-request-thread>` (`[data-help-thread]`, `[data-help-message=instructor|student]`, `[data-help-reply-form]` only when the status is instructor_replied or waiting_for_student). Parent context (`ActingLearner::canViewPrivateLearnerConversations()` false): status and instructor replies only, no question/answer (`[data-help-context]` absent), no form, reply POST is 403.
- Staff queue: Filament `HelpRequestResource` in the admin and instructor panels (`/admin/help-requests`, `/instructor/help-requests`, view page `/{record}`), filters course, status, overdue, summary strip. Query scoped by `HelpRequestAccess::scope`, so a request outside the viewer's scope is 404. View page shows context (question, AI answer, cited pages, video position and preview link, document version), thread, event history, safeguarding flags (`[data-help-safeguarding]`) only when the viewer `can('ai.conversation.view')` (super admin only by default), and header actions reply (optional "I need an answer from the learner"), start, resolve, close.
- Notifications (in-app, plus email when the recipient has an address): created -> assigned instructor, or all managers + super admins when unassigned; reply -> the learner, dedupe `help-request-reply:{message_id}`; student reply -> assigned instructor or managers; overdue -> managers and the assigned instructor, dedupe `help-request-overdue:{id}:{due_at}`. Bodies contain only the lesson title, never the question, answer or reply. A child without email gets the in-app notice and the verified guardians an email copy (existing router).
- Panel: `data-feedback-url` is now the lesson feedback URL; `understood` / `still` are enabled after an answer (no longer disabled placeholders; the `ai.panel.feedback_soon` key is kept in AR/EN but unused). `assistant.js` keeps `message_id` from the SSE `result`; understood shows the thanks notice and hides the actions; still sets `data-state="request_created"` with a notice and a link `[data-ai-request-link]` to the thread; 409 shows the server message and re-enables the buttons.

## Acceptance
- A1 Understood creates no request (one `ai_feedback` row, repeat is a no-op, one audit). Not understood creates exactly one request; five parallel or repeated taps on the same answer return the same request (`ai_message_id` unique, `201` first then `200 request_exists`). The request holds learner, course, lesson, assigned instructor, conversation, question text, AI answer, `ai_status`, cited pages, document version, locale and video position from the conversation, status `new`, `due_at` about now + 24 h, one `created` event, audit `help_request.created`. With no manage-scope instructor the request is unassigned and all managers are notified. Another learner's answer, another lesson's answer or a user-role message id is 404 and creates nothing. Fourth open request on one lesson: 409 `open_limit`; resolving one frees a slot; a different lesson is unaffected. Guard-blocked answers (quiz guard, safeguarding) are 409 `not_escalatable`. Works while the assistant is switched off for the lesson (only `ai.ask` and ownership are required).
- A2 Access: an instructor of another course (and an assigned-elsewhere instructor of the same course) gets 404 on the view page and does not see the row in the list; the assigned instructor sees it in `/instructor/help-requests`; admin and `support` (manage) see all; a student, a parent, a content manager and a suspended staff user cannot open either panel page; calling `ReplyToHelpRequest` / `ChangeHelpRequestStatus` as a non-authorised staff user throws `AuthorizationException` and writes nothing. Safeguarding flags: seed an `ai_safeguarding_flags` row on the conversation; super admin sees `[data-help-safeguarding]`, admin without `ai.conversation.view`, instructor and support do not (and the text is not in the HTML). Filters: course, status, overdue (only `new`/`in_progress` rows with `due_at` in the past) return the expected rows.
- A3 Replies and states: staff reply sets `instructor_replied` (or `waiting_for_student` with the checkbox), stops the SLA (`due_at` null), sets `first_replied_at` once, writes a message, an event and audit `help_request.replied`, and notifies the learner exactly once (`help-request-reply:{id}`; running the action twice with different replies sends two, a retry of the same notice sends none). The notice body has no reply, question or answer text (assert on the stored database notification and on the mail line). Child without email: database notice plus a guardian email copy with no question text. Learner reply is allowed only in `instructor_replied` / `waiting_for_student` (otherwise `not_your_turn`/`closed`), moves to `in_progress`, restarts `due_at`, clears `overdue_at`, notifies the assigned instructor (or managers); someone else's request is 404. Empty and over-long (2001 chars) replies are refused with the lang message. Status changes: new -> in_progress only from new; resolve from any open; close from open or resolved; resolved -> in_progress refused (`bad_transition`); replies on resolved/closed refused (`closed`). Every change writes one event and one audit. Overdue escalation: seed a request with `due_at` 25 h ago; `help:escalate-overdue` sets `overdue_at`, writes one `overdue` event and notifies managers and the assigned instructor once; a second run changes and sends nothing; `due_at` in the future, a replied request, a resolved request are untouched; after a learner reply and a new overdue cycle it escalates again once (new key).
