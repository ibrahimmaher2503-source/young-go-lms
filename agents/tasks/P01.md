# P1 — Identity, roles, localization & family accounts

### T-P1-01 — Localization foundation
- deps: T-P0-03, T-P0-06
- agents: implementer, test-writer, chore
- size: M
- risk: normal
- ai: hook — create `lang/{ar,en}/ai.php` copy deck skeleton (AI spec §15 strings)
- refs: PRD §4.3, Design System §3, Conventions §8, D-011, ED-006, ED-018
- gates: G1-G6

**Goal** Every request runs in AR or EN with correct `lang`/`dir`, and translatable model fields work.
**Steps**
1. Locale resolution middleware: user preference → session → cookie → `Accept-Language` → default (config, Arabic recommended). Optional locale prefix in public URLs (`/ar`, `/en`) for SEO; decide in ADR and record.
2. Locale switcher endpoint (persists to user if logged in).
3. `lang/ar` and `lang/en` structure by module; base keys (common, validation, auth, navigation).
4. spatie/laravel-translatable configured; helper for current-locale fallback.
5. Blade directive/helper for `dir` and `lang` on `<html>`.
**Acceptance**
- A1 Switching locale changes `<html lang dir>` and persists for logged-in users.
- A2 Validation errors appear in the active locale.
- A3 Translatable attribute returns active-locale value with fallback.
- A4 `app:check-translations` passes.
**Out of scope** UI design (T-P1-09/10).

### T-P1-02 — Authentication and profiles
- deps: T-P1-01
- agents: implementer, test-writer, chore
- size: M
- risk: high
- ai: hook — birth year/month feed the AI style tier; never expose birth data to providers
- refs: PRD §6, YG-GAP-ID-001, YG-GAP-FAM-003, Roadmap M1.1, Checklist §3
- gates: G1-G6

**Goal** Secure register/login/logout/reset/verify, profile editing, activation status.
**Steps**
1. Users schema: `username` (nullable unique), `email` (nullable unique, required for non-child), `phone`, `name_ar`, `name_en`, `display_name`, `birth_year`, `birth_month`, `locale`, `timezone`, `status` (active/suspended/deactivated), `last_login_at`.
2. Auth flows (Fortify or custom Actions): register (email + password), login by email or username, logout, forgot/reset, email verification; rate limiters `login`, `register`, `password-reset`.
3. Middleware blocking suspended/deactivated users from protected routes.
4. Profile Actions: update names, avatar (private→public variant), locale, timezone, notification preferences; password change.
5. Certificate names fields + lock rule (locked after first certificate; enforced in Action).
6. Terms/Privacy acceptance recorded at registration with versions in `consents` (YG-GAP-ID-002).
**Acceptance**
- A1 Duplicate email/username rejected with localized errors.
- A2 Suspended user cannot access protected routes (test).
- A3 Login rate limit triggers after configured attempts (test).
- A4 Only birth year/month stored; no full birth date column.
- A5 User cannot change protected fields (status, roles) via profile (test).
**Out of scope** Child accounts (T-P1-05), social login.

### T-P1-05 — Parent-created child accounts and username login
- deps: T-P1-03, T-P1-04
- agents: implementer, test-writer, chore
- size: M
- risk: high
- ai: hook — store consent fields needed for minors' AI gate (O-015); default AI off for minors
- refs: PRD §5.2, YG-GAP-FAM-001/003/005, Arch §10.1, Checklist §3, §14A, PRD §5.3, D-006, YG-GAP-FAM-006
- gates: G1-G6

**Goal** A parent creates child learner accounts that log in with username/password; relationship is explicit and audited.
**Steps**
1. `guardian_profiles`, `guardian_child_links` (status, verified_at, method `created_by_parent|link_code`, consent fields placeholder).
2. Action `CreateChildAccount` (parent only): name(s), username (unique, lowercase), password, birth year/month; role student; link `verified`.
3. Child login via username (reuses auth); email optional for child.
4. Policy helpers: `parentCanAccessChild(parent, child)`; add cases to I02 invariant test.
5. Audit `guardian.child_created`.
**Acceptance**
- A1 Child logs in without email (test).
- A2 Parent sees only linked children; access to unlinked child returns 404 (test).
- A3 Non-parent cannot create child accounts (test).
- A4 Audit entry recorded.
**Out of scope** UI (T-P1-10), link codes (T-P1-06).

**Review requirement — YG-REV-FAM-001 (PRD §29.15)**
Separate account/link provenance, verified guardian authority and versioned consent. Email verification, child creation and possession of a link code are not legal guardian proof. Production minor-account activation requires O-015 and privacy approval; minor AI additionally requires O-014/O-028 and consent.

**Additional acceptance** Synthetic child creation/link confirmation succeeds; unverified/revoked guardian cannot switch context, recover credentials, export child data or receive child notifications. Flag/API tests reject real minor activation without gate evidence. Evidence is required; this task remains todo until implemented and verified.

### T-P1-06 — Link codes and parent context switching
- deps: T-P1-05
- agents: implementer, test-writer
- size: M
- risk: high
- ai: hook — parent context never exposes child AI conversations (O-016)
- refs: YG-GAP-FAM-002/004, Roadmap M1.3, D-006
- gates: G1-G6

**Goal** Existing learners can be linked by confirmed one-time codes; parent can act in a child's context with audit.
**Steps**
1. `guardian_link_codes` (hash, learner_id, expires 48h, used_at); Actions `IssueLinkCode` (learner), `RedeemLinkCode` (parent) → pending link; `ConfirmGuardianLink` (learner) → verified.
2. Context switch: `EnterChildContext` requires recent auth (password confirm); session stores `acting_child_id`; middleware exposes `actingLearner()`; exit action.
3. All learner-facing queries use `actingLearner()`; audit actor=parent, subject=child.
**Acceptance**
- A1 Code single-use and expires (tests).
- A2 Link inactive until learner confirms (test).
- A3 Context switch requires password confirmation (test).
- A4 Actions in child context audited with parent as actor (test).
**Out of scope** Guardian verification beyond this (O-015).

**Review requirement — YG-REV-FAM-002 (PRD §29.15)**
Guardian actions require current authority, recent authentication and actor/subject audit. Unlink/revoke withdraws delegated sessions, future notifications and recovery rights without deleting child-owned records/access. Unknown or boundary-month age is not assumed adult; age-up and consent withdrawal follow approved policy.

**Additional acceptance** Replay old session/link/reset token after unlink; cross-child recovery; concurrent link confirmation; missing/future birth month; age-boundary and consent-withdrawal tests. Logs never contain link codes/passwords or private chat. Evidence is required; this task remains todo until implemented and verified.
