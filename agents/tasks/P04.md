# P4 — Student learning portal & recorded player

### T-P4-01 — Unified EntitlementService
- deps: T-P3-01, T-P1-04
- agents: implementer, test-writer
- size: L
- risk: high
- ai: hook — AI eligibility consumes EntitlementService; replace AI stub
- refs: DMC §6.1, PRD §17.2, §23 (1–5), Arch §5.2, Conventions §5
- gates: G1-G6

**Goal** One authoritative service that decides learner access for every protected resource.
**Steps**
1. `entitlements` (learner_id, course_id, source_type enum: free, purchase, bundle, subscription, manual_grant, manual_payment, legacy_migration; source_ref; starts_at, ends_at, status active/expired/revoked; granted_by; unique (source_type, source_ref, learner_id, course_id)).
2. Actions `GrantEntitlement` (idempotent), `RevokeEntitlement`, `ExpireEntitlements` (scheduled).
3. `EntitlementService::allows(learner, course|lesson, ability)` handling preview lessons, scheduled lessons, expiry; caches per request.
4. Replace the fail-closed stub from T-P3-08/T-P3-10.
5. Invariant tests I01 (access only via service — arch test: only Entitlements module queries `entitlements`), I03/I04 scaffolds (payment ones filled in P8), I05 manual grant without payment.
**Acceptance**
- A1 Duplicate grant with same source creates one row (test).
- A2 Expired/revoked entitlement denies lesson, PDF, AI eligibility (tests).
- A3 Arch test passes (no direct entitlement queries elsewhere).
**Out of scope** Commerce sources (P8).

**Review requirement — YG-REV-ACC-001 (PRD §29.15)**
Preserve independent grants for individual, bundle, subscription, manual and migrated access. Expiring/revoking one source cannot revoke another valid source. Suspended accounts and withdrawn content still fail closed. Cache invalidation follows grant and content changes.

**Additional acceptance** Dataset: purchase + expired plan; manual + refunded purchase; two overlapping grants; exact expiry; future start; revoked link; suspended user. Check player, file, live, AI and direct API consistently. Evidence is required; this task remains todo until implemented and verified.

### T-P4-09 — Layered access: sequence and drip with reason codes
- deps: T-P4-01, T-P4-04, T-P3-04, T-P5-01
- agents: implementer, ui-builder, test-writer
- size: M
- risk: high
- ai: hook — AI eligibility uses the same AccessDecision (locked item → no assistant)
- refs: ED-005, ED-025, YG-GAP-LRN-001, YG-GAP-LRN-002, Arch §11.2
- gates: G1-G7

**Goal** One access decision with clear, localized reasons for every locked item.
**Steps** `EntitlementService::canAccessItem()` returning `AccessDecision`; course `sequence_mode`; item unlock rules (absolute / relative to entitlement or cohort start); reason codes + `lang/*/access.php`; return reason and unlock date for the player integration in T-P4-03; the same decision guards PDFs, resources, live links and AI eligibility.
**Acceptance**
- A1 Dataset test covers every layer and reason code.
- A2 Locked item URL shows the locked state with reason, never the content (test).
- A3 Localized reason payloads verified; locked-state screenshots are required in T-P4-03.
**Out of scope** —

**Review requirement — YG-REV-ACC-002 (PRD §29.15)**
Explicit access modes distinguish learner access, public preview, author preview and support view-as. Public preview exposes only published, explicitly public assets; no hidden course/item, another cohort, private PDF, assessment attempt or adjacent item. Staff preview stays within assigned scope and cannot write learner progress, grades or call AI.

**Additional acceptance** Anonymous and authenticated preview tests include changed item IDs, attachment URLs, future drip, protected live links, suspended course and direct write attempts; every denial has a stable localized reason. Architecture ED-035 defines mode ordering. Evidence is required; this task remains todo until implemented and verified.
